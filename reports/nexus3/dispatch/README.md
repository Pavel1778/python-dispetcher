# Phase 2 · Старт OpenHands и восстановление Python worker

**Решение: оставить Python единственным исполнителем lab DAG.** Изменение устраняет наблюдавшийся повторный запуск после потери ответа, а не ускоряет worker. На одном и том же сценарии `main` запустил **два** разговора для одной родительской задачи, кандидат — **один**. Цена в локальном профиле: **53,99 → 42,66 подписанной задачи/с** (−21,0%). Это основание рассматривать корректность на ревью, не основание для rollout.

[Draft PR #55](https://github.com/Pavel1778/python-dispetcher/pull/55) — **только ревью**, без merge, release, production-миграции или deploy. База — merge [#54](https://github.com/Pavel1778/python-dispetcher/pull/54) **`e866666fb69a13e0edc0c7670b9f56e3561b34c0`** в `main`, не старый PR head `9923916`. Проверяемый продукт — **`a5983a3562ee61bcf49358dbd30289b7629e8e39`**. В [снимке refs](evidence/refs.json) есть оба родителя merge и HEAD рабочей ветки на момент измерений. Отдельной ветки `nexus/3.0-foundation` сервер не вернул. Коммит с этим отчётом не меняет продукт. Предыдущие этапы: [baseline](../README.md), [контракты](../COMPATIBILITY.md), [storage-подмножество Rust](../STORAGE.md).

## Что случилось на самом деле

[Один и тот же скрипт](lost_reply_probe.py) поднял на каждой ревизии приватный PG и локальные HTTP-сервисы. Агентский сервис создал разговор по POST и выдал HTTP-заголовки. В этот момент тест убил **процесс worker** (`SIGKILL`, код −9), до чтения тела ответа. На стенде истёк lease. Первый сменщик получил `503` на **поиск**, второй увидел снова доступный поиск. Ни содержимое БД, ни ответ тестового сервиса не подменялись на вывод «отправки не было».

| Наблюдение | `main@e866666` | Кандидат `a5983a3` |
|---|---|---|
| После гибели первого процесса | 1 POST / 1 удалённый начатый разговор; локального bind нет | То же, в PG `sending`, попытка 1 |
| При недоступном поиске | 2 POST / 2 разных разговора / 2 начальных `run`; привязан второй, попытка 2, `total_iterations=2` | Поиск без POST; `uncertain`, тот же бюджет 1, fence 1→2 |
| Поиск восстановлен | Локально одна запись execution, первый разговор по-прежнему не привязан | Привязан **первый** разговор. Один POST, один `run`, один execution; попытка 1 |

Счётчик на стороне сервиса принципиален: в конце **обе** реализации имеют одну строку execution. Только по этой строке дефект не обнаружить. Исходные наблюдения: [до](evidence/lost_reply_base.json) и [после](evidence/lost_reply_candidate.json).

## Протокол и граница гарантий

* Claim, изменение бюджета и `prepared` теперь коммитятся вместе. Перед вызовом start/continue — отдельный одноразовый переход `prepared → sending` под действующим fence. После него неизвестность означает **только читать**: оригинальная квитанция, полный набор тегов на исходном аккаунте или заданный UUID на исходном agent-server. `nexusdispatch` не превращает App API в идемпотентный POST. Local/Direct передают начальное сообщение на create; у Direct UUID относится к конкретному sandbox.
* Запоздалый отправитель может записать факт принятия, но не присвоить себе новую попытку. Bind, история выполнения и handoff — одна транзакция. После отзыва вместо bind возникает долг остановки; для такого позднего старта исчерпание лимита запросов stop само по себе **не** открывает ветку. Проверка результата отличает ошибку чтения от результата агента. Запоздалый verifier не может отложить новую попытку. Только выигравший переход сообщает об исходе аккаунту.
* Вердикт и обязанность подписать его сохраняются атомарно. Повтор доставки использует прежний UUID; подпись Ed25519 и цепочка не дублируются. Подписанное решение по прогону ждёт подписей задач. Проверка/зависимости по-прежнему опираются на зафиксированные `completed_verified` / `completed_no_changes`, не на обещание агента. Отключённая подпись не подменяется фиктивной. Настроенный, но неработающий ключ оставляет долг, который сможет обработать сменщик.
* SQLx знает, когда **нельзя** reclaim/claim. Он не получает права стартовать OpenHands, проверять результат или подписывать evidence. Отдельные Cloud workflow dispatcher и SQLite control plane не являются lab worker. См. [переходы, SQL для диагностики, условия отката](PROTOCOL.md).

### Что именно испытано

[Тесты](../../../tests/test_dispatch_durability.py) работают с реальным PostgreSQL. [Точки обрыва](../../../tests/dispatch_crash_worker.py) устанавливаются только в тестовом дочернем процессе, не через переменную окружения production worker.

| Где оборван процесс / потеряна связь | Что обязан доказать сменщик |
|---|---|
| До commit claim+intent; после `prepared`, но до `arm` | До commit всё откатывается, в том числе оба счётчика итераций. После commit переходит тот же grant с новым fence, без второй траты бюджета. |
| После `arm`, но **до** POST | На стороне сервиса **ноль** запусков. Читающие сменщики всё равно не получают права повторить отправку. Без новых фактов задача может остаться `uncertain` бессрочно. |
| Принято до чтения ответа; ID уже в памяти; квитанция в PG до bind; внутри транзакции bind | Два процесса восстановления заканчивают DAG, не увеличивая число внешних стартов. Старый fence не привязывает квитанцию поверх нового; трое одновременно сверяющих не создают второй execution. |
| Verdict до подписи задачи; подпись до ack; терминальный переход до подписи прогона | Две задачи остаются `completed_verified`, по одной подписи на нужный commit, одно подписанное `ACCEPTED`, цепочка проверяется отдельно. В случае подтверждённого провала родителя его failure подписывается, ребёнок остаётся `pending`, attempt 0. |
| Исчез start receipt; поиск вернул ошибку, затем запись появилась на второй странице; смена endpoint; malformed result | Ни `503`, ни пустая выдача не разрешают POST на резервном аккаунте. Ошибочный результат с чужим ID не становится вердиктом. Подтверждённый отказ (`403` на create в App fixture) отдельно разрешает обычную политику failover. |
| ACK на продолжение потерян; local/direct create дал ответ с потерей подтверждения | Для продолжения нужен точный **пользовательский** `MessageEvent`, не старый `finished` и не эхо ассистента. Для scoped create даже явный последовательный повтор адаптера даёт тот же UUID и одну начальную активацию; Direct использует один sandbox при отключённом reuse. |
| Отмена в неопределённости, поздняя квитанция и ошибка stop; два verifier; предел циклов на timeout | Другой проект на той же ветке ждёт. Поздний stop не подтверждается другим endpoint. Timeout на последнем цикле не оставляет родителя `running`; ошибка/stop записаны, ребёнок не стартует. |

Девять параметризованных окон с двумя сменщиками в каждом проверяют **два фактических start POST для двух задач**, начальные user events, число execution-строк, обе подписи задач и решение прогона. Десятое окно (`armed_before_send`) преднамеренно не обещает завершения. Остальные проверки дополняют, а не умножают это число. [Результаты конкретных cases на ревизии продукта](evidence/cases.json).

## Измерения: одинаковый worker harness, а не сравнение языков

[Стенд](evidence/host.json): Debian 12, Python 3.11.2, PG 16.2, affinity на 2 vCPU, MemTotal 4 034 452 KiB, **не** целевые 4 CPU / 8 GB. Реальные SQL/HTTP, локальные doubles OpenHands и GitHub. Три отдельных процесса worker на ревизию; каждый делает 100 последовательно зависимых `research_audit`, каждый раз проверяются 100 внешних запусков, 100 подписанных голов и подпись прогона. Время старта сервиса/LLM и сборка Self-QA не эмулируются задержкой. Замеры завершены до общего pytest.

[До](evidence/lifecycle_base.json) · [после](evidence/lifecycle_candidate.json) · [промежуточный `419e2a8`](evidence/lifecycle_419e2a8.json). Идентичный [harness](../../../benchmarks/dispatch_lifecycle.py), SHA-256 `a8bb6743594aa4f833592604916b82cf2ce66216fd8ab38db75aaee398471cb5`. Перцентили nearest-rank **внутри** каждого прогона, выше — медианы, не объединённый p99. Тики идут без ожидания poll interval. RSS относится к процессу, не ко всему хосту. Счётчик execute **не** включает служебные сообщения пула и протокольные BEGIN/COMMIT и не равен числу сетевых пакетов. Рост числа запросов на 29,8% виден в данных; небольшое изменение RSS не доказывает экономию памяти на production.

**Рестарт уже привязанного разговора:** 5 DAG × 2 задачи на ревизию, SIGKILL между bind родителя и выдачей ребёнка, интервал worker 0,3 с / наблюдателя 0,05 с. Медианы: request→first bind **251,70 → 268,15 мс**, запуск сменщика→bind ребёнка **206,63 → 206,47 мс**, request→signed acceptance **0,8217 → 0,8367 с**. В каждом опыте ровно два старта и обе подписи задач проверены по SHA. [До](evidence/restart_base.json) · [после](evidence/restart_candidate.json) · [промежуточный](evidence/restart_419e2a8.json). Пять быстрых DAG не дают SLO и не предсказывают tasks/hour на реальном проекте.

**Отдельно — storage probe:** четыре раунда × 200 grant на driver, PG 17.12 в hosted CI, одна прогретая связь, одинаковые клоны, без OpenHands. Медианы Python **405,80** и SQLx **429,25** grant/с; в третьем раунде SQLx **47,0** grant/с с p99 **171,072 мс**. [Все раунды, параметры и SHA checkout](evidence/storage_probe_ci.json), выброс не исключён, причина не установлена. Python возвращает полную строку, Rust — id/token. Это **не** измерение Rust worker: такого worker здесь нет.

| [`a5983a3` — продукт](https://github.com/Pavel1778/python-dispetcher/actions/runs/44802716516) | **2113 passed, 38 skipped** / 443,81 с | **2126 passed, 25 skipped, 1 warning** / 471,25 с | 28 passed / 3,52 с |

Что исправлено после красного прогона: прежний сценарий failover считал `503` доказательством отсутствия старта. Не меняли классификацию на небезопасную: разделили проверку доказанного отказа и проверку `503` с **запретом** повторной отправки. Локальная проверка пула видела `size=8, idle=7`: psycopg_pool резервирует slot *до* фонового AddConnection. Тест допускает до 2 с на завершение этой операции, не увеличивая предел пула и не отменяя конечного `idle == size`, `waiting == 0`. Ещё три целевых теста воспроизвели поздний reverify, двойную запись о восстановлении аккаунта и застрявший последний timeout; после исправления целевая группа из восьми модулей дала **197 passed**.

Не складывать число тестов двух jobs. В Python CI из 25 skips: 19 SQLx-кейсов (работают в отдельном job), 3 MinGW, 1 pooler, 1 реальный локальный agent-server, 1 реальное облачное dev-задание. В notices `10 requires SQLx` — число сгруппированных строк вывода, не число параметризованных cases. Локально сверх этого не исполнялись 9 decision parity и 4 Android SDK cases, итого 38 skips. Для Rust запускаются также `cargo build --workspace --release --locked` (плюс release example) и `cargo test --workspace --locked`. Тесты проверяют шесть защит от reclaim для `prepared`, `sending`, `uncertain`, `accepted`, `identified` и legacy `pending_start`. В hosted jobs фиксируется **фактический** checkout, не неявный merge ref. Локальная Python suite не заменяет сборку Rust.

## Совместимость и эксплуатация

* [Upgrade старой, непустой БД](evidence/upgrade.json): `LabStore` из архива merge записал старую квитанцию `pending_start`; после истечения lease применена ровно `0043_lab_dispatch.sql`, второй проход — 0, `verify_schema()` — пусто. Состояние/квитанция/счётчики не изменились, чужого grant/reclaim нет. **43/43** исторических checksum и **51/51** shapes таблиц сохранены; итого 44 миграции, 54 таблицы, 621 колонка, 172 индекса, 94 FK. У трёх новых таблиц включён RLS, ни у `anon`, ни у `authenticated` нет табличных привилегий на них в этом стенде. Это не аудит прав существующего production instance.
* [Wire](evidence/wire.json) совпал с [зафиксированным контрактом](../evidence/wire_contract.json): 9 HTTP cases, 5 MCP сообщений, 4 stdio-ответа. Сравниваются статусы, выбранные заголовки и тела на фиксированных данных, в т. ч. отказ без auth и чужой проект. Не утверждаем равенство всех маршрутов по девяти примерам.
* [Studio](evidence/studio.json): 9/9 экранов desktop/mobile совпали по декодированным RGB и SHA-256 PNG, все 15 assets совпали с reference. Один и тот же Chromium 153.0.8010.0; live provider и физический телефон для этого не нужны. Дерево `orchestration/studio` на базе и кандидате `103e6acfe8cec5220b7f1c318bb885e938e2a107`. CLI/MCP server и Cargo.lock не заменялись.
* Для **будущего** обновления требуется остановить выдачу и все inline/external workers, сверить незакрытые старые старты на исходных аккаунтах, сохранить и проверить восстановление snapshot; только затем рассматривать миграцию. Для отката сначала погасить/разобрать открытые intents, stop и обе очереди подписей. Не запускать старый worker против живого нового журнала и не «лечить» `uncertain` очисткой строк. Потеря видимости исходной учётной записи, неполная выдача и отсутствие квитанции доставки файла требуют расследования, а не повторного POST. Контекст и подписи принадлежат проекту, их не надо публиковать для диагностики.

**Не подтверждено:** exactly-once у внешнего провайдера, доставка при вечной недоступности поиска или ключа, отсутствие orphan sandbox при сбое самого provisioning, общая производительность production, реальная смена двух облачных аккаунтов, Self-QA конкретного проекта, длительный soak и целевой 4 CPU / 8 GB. Телеметрия здоровья аккаунта не транзакционна с внешней системой. Следующий отдельный gate, если владелец одобрит: дать цену каждого запроса журналирования на целевом стенде и проверить контракт lookup/stop на специально разрешённых тестовых аккаунтах. Ни слияния, ни перехода на Rust для этого отчёта не требуется.

## Как повторить безопасно

Нужны зависимости проекта, PostgreSQL client/server одной major-версии на PATH, непривилегированный Linux-пользователь. Для снимков — Playwright + Chromium + Pillow. **Не задавать адрес существующей БД:** wrapper создаёт новый socket-only кластер и очищает окружение; suite сбрасывает схемы и создаёт роли. Запуск сравнений последовательно, без параллельной нагрузки:

```sh
root=$PWD; out=$(mktemp -d); base=e866666fb69a13e0edc0c7670b9f56e3561b34c0
git archive -o "$out/base.tar" "$base" && mkdir "$out/base" && tar -xf "$out/base.tar" -C "$out/base"
git get-tar-commit-id < "$out/base.tar" > "$out/base/.git-archive-commit"
test "$(cat "$out/base/.git-archive-commit")" = "$base"
probe="$root/reports/nexus3/dispatch/lost_reply_probe.py"
profile="$root/benchmarks/dispatch_lifecycle.py"
(cd "$out/base" && tools/with_disposable_postgres.sh python "$probe" "$out/red.json")
tools/with_disposable_postgres.sh python "$probe" "$out/green.json"
(cd "$out/base" && tools/with_disposable_postgres.sh python "$profile" --tasks 100 --rounds 3 --out "$out/base.json")
tools/with_disposable_postgres.sh python "$profile" --tasks 100 --rounds 3 --out "$out/product.json"
tools/with_disposable_postgres.sh python benchmarks/forensic_workload.py restart --repeat 5 --out "$out/restart.json"
tools/with_disposable_postgres.sh python reports/nexus3/dispatch/upgrade_probe.py "$out/base" "$out/upgrade.json"
tools/with_disposable_postgres.sh python reports/nexus3/capture_wire.py "$out/wire.json" --compare reports/nexus3/evidence/wire_contract.json
tools/with_disposable_postgres.sh python tools/studio_snapshots.py "$out/screens" --compare reports/nexus3/studio
tools/with_disposable_postgres.sh python -m pytest -q -p no:cacheprovider -rfEs --junitxml="$out/full.xml"
```

Для локального Rust gate собрать оба release-бинаря с `--locked`, указать `NEXUS_RUST_BIN` и `NEXUS_CLAIM_PROBE` (абсолютные пути) и убедиться, что `tests/test_rust_parity.py tests/test_rust_claim.py` прошли **без** SKIPPED. [Точные команды в CI](../../../.github/workflows/tests.yml). После успешной проверки остановиться на решении владельца.
