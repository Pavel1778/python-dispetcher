# NEXUS: аудит и техническая спецификация (проект)

Статус: **предварительная**, 2026-11-07. Основана на checkout main
`7cffe543527951a188c44172996dd14e98946dd0` и запросе владельца. Это не
утверждение, что NEXUS уже работает. Второй аудит другой копии, особенно её
Evaluation Engine, отсутствует: его исходники и отчёт необходимо получить и
сопоставить до утверждения спецификации и подключения новых компонентов к
исполнению. Текущий документ — база для этого сравнения.

## 1. Граница продукта

NEXUS владеет целями, планами, контекстом, политиками, доказательствами и
состоянием; модели предлагают структурированные действия, а backend проверяет
их и исполняет разрешённое. OpenHands — заменяемый исполнитель. Проект —
граница доступа и контекста; смена LLM не меняет аккаунт исполнителя.
Неизвестные требования и предполагаемые решения не выдаются за требования
пользователя. Полная автономность распространяется только на разрешённые
политикой действия. Удаление данных, изменение секретов/прав и merge в
защищённую ветку по умолчанию запрещены.

## 2. Фактический аудит checkout на момент подготовки спецификации

Позднейшие изменения: добавлены проекты, ручные версионированные планы, PWA,
голосовой ввод и вложения проекта, а также опциональные GitHub-действия с
подтверждением. Их фактические границы: [DEVELOPMENT-LAB.md](DEVELOPMENT-LAB.md).
Также добавлено сканирование очереди мимо задач с неудовлетворёнными зависимостями; см.
[NEXUS-OPERATIONS.md](NEXUS-OPERATIONS.md). Остальные пробелы остаются.

## 3. Модули и границы доверия (цель)

1. **Projects / Policy**: авторизация на каждый запрос, проект, репозиторий и
   действие. Не полагаться только на фильтр UI или переданный клиентом ID.
2. **Goal / Planning**: пользовательский запрос, ограничения, критерии,
   открытые вопросы и происхождение решений; versioned структурированный план.
   LLM-ответ валидируется backend до транзакционной записи.
3. **Scheduler / Execution**: DAG внутри проекта и версии плана; только
   зависимости с принятой оценкой разблокируют потомков. Атомарное назначение,
   lease, idempotency и bounded retry переиспользуют Dispatcher. Нет сетевых
   вызовов внутри открытой DB-транзакции. Восстановление безопасно при повторах.
4. **Account Manager**: отдельный account ID, endpoint, identity, лимит,
   статус и ссылка на секрет; атомарное резервирование слота; явно проверенные
   права в проекте для нужного действия. При неизвестных правах — fail closed.
5. **LLM Gateway**: provider adapter с единым структурированным контрактом;
   ограниченные timeout/retry/fallback для rate-limit, quota и transient ошибок;
   сохранять provider/model и результат, не ключи. Недоступность провайдера не
   должна менять OpenHands account. Невалидный ответ не исполнять.
6. **Memory / Context**: global, project, execution и knowledge. Каждая запись
   имеет scope, project_id где применимо, provenance (`VERIFIED`, `INFERRED`,
   `UNKNOWN`), ссылку на источник и время. Извлечение сначала авторизуется и
   фильтруется по project_id, затем ограничивается по размеру; FTS до pgvector.
7. **Evaluation / QA**: отдельный доверенный runner в изоляции собирает
   evidence с происхождением, конкретным commit SHA, временем, командой,
   exit status и ссылкой/хешем лога. Отчёт агента — неподтверждённое утверждение,
   не доказательство успешного запуска. QA не подменяет детерминированные gates.
8. **Notifications / UI**: durable события и уведомления с авторизацией;
   один API для клиентов. UI отображает неизвестное/заблокированное честно.
   Web, Desktop, Android и realtime не заявляются реализованными.

## 4. Контракты и состояния (предлагаемые)

- **Goal**: `project_id`, исходный текст, список требований `{text, source,
  confidence}`, ограничения, критерии успеха, вопросы, версия. Источники не
  подменяются; неразрешённые вопросы могут блокировать опасную работу.
- **Plan**: `project_id`, `goal_id`, версия, задачи `{id, description,
  acceptance[], inputs[], constraints[], dependencies[], executor_hint,
  max_attempts}`. Идентификаторы уникальны в плане, все зависимости в том же
  плане, нет циклов или ссылок на себя. Публикация плана атомарна.
- **Task**: NEXUS lifecycle `planned -> ready -> dispatched -> running ->
  result_received -> evaluating -> completed | rework | blocked | failed`.
  `ready` требует принятия всех зависимостей; `rework` потребляет ограниченный
  бюджет; `blocked` не означает успех. Отмена и повтор идемпотентны. Это
  **целевая** модель, а не переименование существующих состояний Dispatcher.
- **Evaluation**: `ACCEPTED | REWORK | BLOCKED | REJECTED`, ссылки на evidence,
  критерии, проверяющий и версия политики. `ACCEPTED` невозможно без всех
  обязательных, достоверных, актуальных проверок; отсутствующее свидетельство
  означает блокировку, а не успех. Финальный QA `READY | READY_WITH_CONDITIONS |
  NOT_READY` отделён от оценки отдельных задач.
- **Action policy**: backend проверяет actor, project, repository, permission,
  фактическую идентичность и policy revision до любого побочного действия;
  решение записывается в audit log. Никаких произвольных shell/SQL команд от LLM
  на хосте backend. Sandboxed runner требует лимитов и контроля доступа к сети и
  секретам; выполнение непроверенного кода — отдельная угроза.

### API v1 (целевой контракт, маршруты пока не существуют)

JSON через существующий backend, с серверной авторизацией и CSRF для cookie;
ID проекта в пути обязателен. `POST` с `Idempotency-Key`; повтор ключа с другим
телом — конфликт, а не повтор старого результата.

- `POST/GET /api/v1/projects`, `GET /api/v1/projects/{project_id}`.
- `POST /api/v1/projects/{project_id}/goals`; `GET .../goals/{goal_id}`.
- `POST .../goals/{goal_id}/plans`, `GET .../plans/{plan_id}`; публикация
  отдельной командой после валидации всех задач и зависимостей.
- `GET .../tasks/{task_id}`, `POST .../tasks/{task_id}/cancel|retry`.
- `GET .../tasks/{task_id}/evaluations`, `GET .../evidence/{evidence_id}`.
- `GET .../events`, `GET .../notifications`; курсор/пагинация и проверка scope.

Все записи и чтения проверяют membership; 404 для чужого ресурса без раскрытия
существования. Не реализовывать HTTP маршруты до решения модели пользователей
и изоляции существующих данных. Machine token не должен становиться обходом
project-scoping; service role и прямые Supabase клиенты — отдельные угрозы.

## 5. Данные и безопасная миграция

Использовать существующие `workflows`, `tasks`, `conversations`, `task_events`,
а не параллельную очередь. Новые сущности: `projects`, `project_members`,
`project_repositories`, `plan_versions`, `task_dependencies`, `task_attempts`,
`agent_accounts`, `agent_runs`, `memory_entries`, `knowledge_documents`,
`evaluations`, `evidence`, `notifications`, `audit_events`. Связи должны
проверять соответствие project_id в БД (составные FK/constraints), а не только
на уровне Python. `global` memory требует отдельной явной политики доступа.

Порядок: backup и проверка схемы/прав; additive таблицы и nullable ссылки;
явное назначение legacy-данных владельцем в проект или карантин (не угадывать);
проверка данных и конфликтов, затем constraints/индексы; только после
совместимых чтений/записей закрыть старые неограниченные RLS policies. RLS и
GRANT необходимо протестировать реальными DB roles, включая service-role bypass.
Изменение механизма `completed` нельзя включать без миграции и совместимости:
старые завершения не доказательства, помечаются legacy/unverified. Миграции
версионируются, проверяются на пустой и заполненной БД, с rollback/backup
процедурой; запуск на production только после проверки и разрешения оператора.

## 6. Критерии реализации и приёмки этапов

0. Сравнить обе версии Evaluation Engine и свести аудит; утвердить эту спецификацию.
1. Изоляция: два проекта, запрещённые cross-project read/write/dependency и
   context retrieval, RLS/grants и безопасная миграция legacy — DB integration.
2. Accounts: изоляция секретов, проверка прав, лимиты, конкурентный claim,
   ручное назначение, восстановление — fake Cloud и PostgreSQL integration.
3. Gateway: схемы ответов, таймауты, квоты, fallback, редактирование секретов,
   запись модели; имитация отказов без платных запросов.
4. Planner/DAG: проверка циклов, чужих ссылок и budget, атомарная публикация;
   конкурентные scheduler/lease тесты и устойчивость к рестарту.
5. Memory: provenance, ограничение контекста, изоляция и полнотекстовый поиск.
6. QA: независимый runner, неполные/устаревшие/поддельные evidence блокируют
   приёмку; ограниченные rework, фактический Git SHA, воспроизводимые логи.
7. Notifications, UI и клиенты: сквозные тесты авторизации и доступности.
8. Hardening: security review, восстановление после сна, отказ внешних систем,
   нагрузка и проверка живых интеграций. Ни один из этапов не считается
   завершённым по одному только ответу модели.
