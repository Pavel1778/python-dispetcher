## 1. What the repository is

A durable **control plane** that orchestrates OpenHands agent conversations. It
owns task state, leases, assignment and recovery; it does **not** own the
runtime (conversations execute in the OpenHands agent-server / Cloud).

```
project ──▶ repositories (explicit links)
   │
   └─▶ workflow ──▶ Sr conversation ──sr_create_task──▶ task ──▶ Jr conversation
                          ▲                                     │
                          └────────────── result ───────────────┘
   task/workflow result ──▶ Evidence Trust Engine (Ed25519)
                            ──▶ VERIFIED / UNVERIFIED / FAILED / BLOCKED
```

## 2. Architecture map (verified against the code)

### 2.1 Transports

Four clients implement **one** surface, so the dispatcher and Sr runtime do not
know which is in use:

| Client | Target | Selection |
|---|---|---|
| `cloud_client.py` | OpenHands Cloud V1 (`/api/v1/app-conversations`, Bearer) | `OPENHANDS_TRANSPORT=app` |
| `cloud_direct.py` | a sandbox the client provisions, then its agent-server | `OPENHANDS_TRANSPORT=direct` (**default**) |
| `openhands_client.py` | a local/remote agent-server v1.50.1 | used by Sr/Jr + local tests |
| `local_runtime.py` | a local agent-server, for the e2e scripts | tests only |

`build_cloud_client` picks between `cloud_client`/`cloud_direct` from the
transport. `CloudClient.supports_repository_selection` is `True`;
`CloudDirectClient`'s is `False` (the direct sandbox starts empty, governed by
`OPENHANDS_DIRECT_REPO_MODE`).

### 2.2 Durable state

`cloud_store.py` (`PostgresStore`) is the PostgreSQL/Supabase task store:
atomic claim (`SELECT ... FOR UPDATE SKIP LOCKED` + lease), idempotency keys,
`force_transition` for legal-path recovery, the sandbox/conversation route
table, `REQUIRED_COLUMNS` schema guard, and a connection self-heal
(`_tx()` replaces a dropped connection on evidence only, with
`RECONNECT_BACKOFF_SECONDS`). Server-side prepared statements are **off**
(`prepare_threshold=None`) for pooler safety. `transition()` returns the row it
wrote (`UPDATE ... RETURNING *`), not a re-read.

### 2.3 Orchestration

- `dispatcher.py` / `cloud_dispatcher.py` — one tick = reconcile → recover →
  advance → dispatch; the only place that decides task state from runtime
  signals. Two-phase create (start → poll → bind), allowlist, bounded retry.
- `sr_runtime.py` / `sr_tools.py` — Sr delegates through **client tools**
  (`sr_`-prefixed to avoid colliding with built-in tool names); `workflow_id` is
  never taken from the model.
- `workflow_verifier.py` — the single writer of a workflow's terminal state,
  deciding from durable state (not Sr text); blocks a childless workflow after
  `sr_idle_timeout_seconds`.

### 2.4 Autonomous lab

`nexus_lab_store.py` (runs/tasks/notifications, one active run per goal, atomic
claim with lease, dependency gating on `completed_verified`), `nexus_lab.py`
(`OpenHandsExecutor` dispatch+poll — never decides completion; `GitVerifier`
checks the real remote branch/commit; `LabScheduler` one tick =
reclaim → poll → verify → record → claim → authorize → dispatch → decide),
`lab_worker.py` (the loop, no per-run state so a restart is a non-event), and
`nexus_planner.py` (validates ids/deps/cycles before storing a plan).

The web server advances runs itself by default (`NEXUS_LAB_INLINE`, default on)
and registers an `inline` heartbeat; `python -m orchestration.lab_worker` runs
the same loop as a separate process. Both are defined in `render.yaml` (web +
worker) and `docker-compose.yml`.

### 2.5 OpenHands multi-account, pool and failover

- `nexus_openhands_accounts.py` — one account per row; the API key is
  **Fernet-encrypted** with `NEXUS_SECRET_KEY` (`secrets.py` is the single
  cipher; a missing key is a hard refusal, never a plaintext write). Identity is
  verified via the account API before it is trusted.
- `openhands_pool.py` — the four selection modes (`manual`, `auto`, `failover`,
  `load_balancing`). "Usable" = `state='active'` AND `enabled` AND health not
  `unavailable`. Load is **derived** from in-flight `nexus_run_tasks`, not a
  counter.
- `openhands_router.py` — `AccountRouter` chooses per task and builds the
  hand-off context; `tried_accounts` makes failover terminate. A conversation
  cannot move between accounts, so a switch is a *new* conversation with the
  context passed in the first message; the old account is never polled again.
- `openhands_diagnostics.py` — the one diagnostic engine. Four earned statuses:
  `VERIFIED` / `FAILED` / `BLOCKED` / `UNVERIFIED`. `report.ok` is true unless
  something FAILED.

### 2.6 Projects, evidence, security

- Project execution binding (`nexus_binding.py`): `authorize_dispatch` is the
  single gate, re-run before a conversation is created and before a task is
  queued; a `BEFORE INSERT/UPDATE` trigger keeps `tasks.repository_id`
  canonical.
- Evidence Trust Engine (`evidence_trust.py`): Ed25519 over a canonical
  encoding; only a trusted asymmetric signature yields `VERIFIED`. Project-scoped
  records sign `project_id` (format v2).
- Security controls verified in code: server-side sessions + CSRF
  (`web_auth.py`), proxy-aware client IP (`TRUSTED_PROXY_HOPS`, rightmost trusted
  hop), login ceilings (per-IP + endpoint-wide), redirect refusal
  (`_NoRedirect` in `cloud_client`, `_SameOriginRedirect` in
  `openhands_client`), Fernet secret cipher, archive-safety validation before any
  row is written (`archive_safety.py`), project isolation as a **404** not a 403,
  and redacted `__repr__` on credential-bearing clients. No secret is committed
  (pattern scan for `sk-`/`ghp_`/`AIza`/PEM headers found nothing).

## 3. Findings

Severity: **F-1** load-bearing (pool silently inactive), **F-2** documentation
accuracy, **F-3** maintainability, **F-4** environment.

### F-1 (load-bearing, documented but unfixed): the account pool is off on any deployment with a login

- **Where.** `web_server._project_principal` stores a studio-added account under
  `user:<login>` when a session/login exists (`principal_for_session`), but both
  loop paths build the router for `machine:default`:
  `web_server.py:586` calls `build_account_router(self.store)` (default
  principal) and `lab_worker.py:161` calls it with
  `principal="machine:default"`.
- **Effect.** `build_account_router` returns `None` when
  `list_accounts(principal)` is empty, so with `AUTH_USERNAME` configured (the
  normal case) the pool is **never switched on**: the loop keeps running every
  task under the process-wide `OPENHANDS_API_KEY`. Adding accounts in the studio
  changes nothing about execution.
- **Evidence.** `build_account_router` (`openhands_router.py:225`) returns `None`
  unless the principal has accounts; the two call sites both use
  `machine:default`; `POST /api/openhands/accounts` uses
  `self._project_principal()`. This matches the note in `AGENTS.md`
  ("`build_account_router` asks for the accounts of `machine:default`, while an
  account added in the studio belongs to `user:<login>`, so on a deployment with
  a login the pool is never switched on").
- **Status.** Reproduced by reading the call sites; **not fixed** in this audit
  step (a fix is a behaviour change to the loop and belongs with its own test).
  Recommended fix: build the router for the same principal the accounts were
  stored under (derive it from the configured owner), and cover it with a test
  that stores an account as `user:owner` and asserts the loop routes through it.

### F-2 (documentation accuracy): README describes a UI that no longer exists

- **Where.** `README.md:244` ("The dashboard now has a **Лаборатория** tab and a
  **GitHub** tab") and the section that follows it.
- **Reality.** The studio (`orchestration/studio/`) is one application: chat
  history, the conversation and composer, and a workspace with two tabs
  («Файлы», «Агент»). Its only tab action is `ws-tab`; there is no Лаборатория or
  GitHub tab. `AGENTS.md` states the studio removed both. The **routes** for
  those features are unchanged and reachable through the API, the CLI and MCP.
- **Fix.** Corrected in this commit: the section now says the features are
  reachable through the API/CLI/MCP and are not screens in the studio.
- **Related (not fixed here).** `AGENTS.md` "still open" item 7 lists further
  docs that describe the removed interface: `docs/AUTONOMOUS-LAB.md`,
  `docs/NEXUS-AUDIT.md`, `docs/NEXUS-SPEC.md`,
  `docs/MASTER_COMPLETION_AUDIT.md`, `docs/MASTER_COMPLETION_ROADMAP.md`. Those
  are historical reports and were left as written; rewriting them is a separate,
  larger documentation task.

### F-3 (maintainability): two migrations share the number `0025`

- **Where.** `migrations/0025_task_preferred_account.sql` and
  `migrations/0025_task_time_limit.sql` both exist and both `ALTER
  nexus_run_tasks`.
- **Effect.** None at runtime: the runner applies every `*.sql` in lexical order
  and records each by **filename** (`schema_migrations.filename` is the PK), so
  both apply — verified on a fresh database (24 applied, both `0025` files
  present). The risk is purely human: two files with one number invite a future
  edit to the wrong one and break the "one change, one number" convention.
- **Recommendation.** Renumber one to `0026` in a follow-up (a rename is safe:
  the runner keys on the filename, but a deployment that already applied it will
  re-run the renamed file, so the statement must stay idempotent — both are).

### F-4 (environment): 8 tests skip for missing external tooling

Not defects; recorded so the coverage number is honest. See §0. The three
Android and three Windows skips need SDKs absent from this sandbox; the pooler
test needs a PgBouncer; the browser tests skip only where Chromium is absent
(installed and green here).
