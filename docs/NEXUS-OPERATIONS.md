# NEXUS: руководство по текущей реализации

Этот документ описывает **фактически реализованную часть**, а не все функции
из целевого продукта. Общая архитектура и открытые вопросы — в
[NEXUS-SPEC.md](NEXUS-SPEC.md).

## Что работает

- Проекты, их владелец, черновики целей и базовые события проекта хранятся в
  PostgreSQL. Сессия и machine bearer используют существующую авторизацию.
- Можно вручную создать несколько версий плана для цели. План состоит из задач,
  критериев приёмки и зависимостей. Backend проверяет корректность и отсутствие
  циклов, транзакционно сохраняет план и позволяет владельцу его согласовать.
- Вкладка **Проекты NEXUS** позволяет создать проект и цель, составить и
  просмотреть план, согласовать его. Согласование **не запускает исполнение**.
- Оригинальный Dispatcher по-прежнему доступен через его старый интерфейс и API.
  В его очереди ожидание зависимости или подтверждения больше не мешает запуску
  независимой задачи с более низким приоритетом.

## Чего пока нет

План создаётся вручную: автоматического LLM-планировщика, LLM Gateway,
проектно-изолированного диспетчеризации задач, мультиаккаунтного OpenHands,
project memory, независимого Evaluation/QA, GitHub App, Rust CLI, React/PWA,
Desktop и Android-клиентов **нет**. Плановые задачи не являются реальными
задачами в очереди Dispatcher; их статусы, ресурсы и критерии не проверяются.
Не используйте отметку «согласован» как свидетельство выполнения или разрешение
на merge. Старое состояние `completed` означает завершение по правилам
Dispatcher, а не подтверждение тестов, Git или QA.

## Запуск и база

Требуются Python 3.10+, PostgreSQL и зависимости из `requirements.txt`.
См. [DEPLOY.md](../DEPLOY.md) для необходимых переменных, настройки логина,
токена, OpenHands, защиты и запуска Render. База нужна даже для проектных
черновиков. Реальное подключение Supabase/Render и состояние production-схемы
для этой версии не подтверждены.

Перед развёртыванием:

1. Проверьте актуальные backup и возможность восстановления, целевой DSN,
   существующие таблицы и историю миграций. Не запускайте тесты на production.
2. Изучите `0009_nexus_projects.sql` и `0010_nexus_plans.sql`. По умолчанию
   `AUTO_MIGRATE=true`: приложение применит новые SQL-файлы при подключении.
   При управляемом развёртывании установите `AUTO_MIGRATE=false` и примените
   миграции отдельно по согласованной процедуре. Не меняйте уже применённые
   файлы миграций и не считайте локальный тест проверкой production.
3. Проверьте права БД и Supabase RLS. Новые `nexus_*` таблицы закрыты для
   `PUBLIC`, `anon` и `authenticated` и включают RLS без клиентских политик;
   доступ осуществляется через backend. DB owner/service role может обходить
   RLS и должен оставаться доверенным. Существующие legacy-таблицы и их RLS
   этой работой не изолируются.
4. Проверьте `/healthz`, вход, создание проекта/цели/плана и сохранение после
   перезапуска на безопасном тестовом окружении. Реальный OpenHands и GitHub
   следует проверять отдельно с разрешёнными аккаунтами и репозиториями.

Render Free может засыпать; это означает, что цикл Dispatcher не работает
непрерывно. Долговечные записи не гарантируют 24/7-доступность worker.

## Авторизация и изоляция

Существующая система рассчитана на одного сконфигурированного владельца:
`AUTH_USERNAME` + пароль и сессия либо `WEB_AUTH_TOKEN`. Bearer действует от
имени сконфигурированного владельца, то есть имеет доступ ко всем его проектам;
если имя не настроено, он представляет `machine:default`. Смена
`AUTH_USERNAME` меняет principal: автоматического переноса проектов нет.
Системы выдачи и ротации прав нескольким реальным пользователям пока нет.

Новые endpoints проверяют membership проекта на backend. Неверный или чужой
ID возвращает 404. План можно создать как участник, согласовать — только как
владелец. По умолчанию создаётся только владелец; UI/API управления другими
участниками не реализован. Старые `/api/workflows`, `/api/tasks` и прочие
legacy-маршруты остаются owner-level и не обеспечивают изоляцию по проектам.
Не предоставляйте их недоверенным пользователям.

Браузерным POST/PATCH требуется CSRF-токен из `/api/session`. Machine API
использует `Authorization: Bearer …`; храните токен как секрет, не вставляйте
его в файлы проекта и логи. Не пересылайте API-ключи LLM или OpenHands в цели,
планы, критерии или историю событий.

## Как создать план в интерфейсе

1. Во вкладке **Проекты NEXUS** создайте проект и сохраните цель.
2. Нажмите **Планы цели**. Введите одну задачу на строку в формате:

   ```text
   audit | Анализ | | Изучены требования и ограничения
   backend | Backend | audit | Добавлены тесты; Сборка успешна
   frontend | Frontend | audit | Интерфейс проверен
   qa | Приёмка | backend, frontend | Результаты рассмотрены
   ```

   Поля разделяются `|`: ID, название, зависимости через запятую, критерии
   через `;`. ID уникален в рамках плана и состоит из ASCII-букв, цифр, `_`,
   `-`, начиная с буквы или цифры. Эта форма не поддерживает сами символы
   `|` и `;` внутри соответствующих полей; API принимает структурированный JSON.
3. Сохраните версию. Выберите её в списке, проверьте задачи и зависимости и
   нажмите **Согласовать план**. Это фиксирует решение владельца, но не
   запускает работу. Следующее сохранение создаёт новую версию; при её
   согласовании предыдущая согласованная версия становится `superseded`.

## API планов

Все пути относятся к текущему проекту; записи клиента не являются источником
прав доступа. Каждый запрос требует действующей сессии или machine bearer.

| Метод | Путь | Результат |
|---|---|---|
| POST | `/api/v1/projects/{project_id}/goals/{goal_id}/plans` | Создать проверенный draft |
| GET | `/api/v1/projects/{project_id}/goals/{goal_id}/plans` | Список версий, новые сначала, до 200 |
| GET | `/api/v1/projects/{project_id}/plans/{plan_id}` | План, задачи и зависимости |
| POST | `/api/v1/projects/{project_id}/plans/{plan_id}/approve` | Согласовать draft от имени владельца |

Пример тела POST:

```json
{
  "tasks": [
    {"id": "audit", "title": "Аудит", "acceptance": ["Документированы риски"]},
    {"id": "api", "title": "API", "description": "Реализовать endpoint",
     "acceptance": ["Добавлены тесты"], "dependencies": ["audit"], "max_attempts": 3}
  ]
}
```

- Допустимы только указанные поля; `tasks` содержит 1–100 задач.
- У каждой задачи обязателен непустой `title` и 1–20 критериев `acceptance`.
  `description` необязателен, `max_attempts` — целое 1–10 (по умолчанию 3),
  `dependencies` — до 20 уникальных ID задач **того же плана**.
- Неизвестные задачи, повторы, ссылка на себя, циклы, превышение ограничений и
  неизвестные поля вызывают 400; неполный план не записывается.
- Заголовок `Idempotency-Key` при создании плана не обязателен, но рекомендуется.
  Повтор идентичного запроса той же цели возвращает существующую версию (200);
  изменение содержимого или автора при том же ключе — 409. Ключ ограничен 200
  символами и не является секретом. Создание новой версии возвращает 201.
- Согласование повторяемо для согласованного плана. Согласование новой версии
  заменяет прежнюю; `superseded` нельзя согласовать повторно. История событий
  содержит метаданные создания и согласования, но ещё не является полноценным
  неизменяемым security-аудитом.

## Тестирование

Нужна **одноразовая** тестовая PostgreSQL: тесты удаляют таблицы и очищают
данные. Никогда не устанавливайте `TEST_SUPABASE_DB_URL` или `SUPABASE_DB_URL`
на production при выполнении тестов.

```bash
python -m pip install -r requirements.txt -r requirements-dev.txt
export TEST_SUPABASE_DB_URL='postgresql://.../disposable_test_db'
python -m ruff check .
python -m pytest -q -p no:cacheprovider
```

Отдельно: `python -m pytest tests/test_nexus_planning.py
 tests/test_nexus_projects.py -q -p no:cacheprovider`. Без DSN тесты БД
пропускаются, поэтому такой запуск не подтверждает миграции, изоляцию или
конкурентность. Тест pooler дополнительно требует `TEST_POOLER_DSN`. Проверка
живых провайдеров, OpenHands, production RLS и Render — отдельные задачи и не
подменяются fake-серверами.
