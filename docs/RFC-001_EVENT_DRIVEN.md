# RFC-001: Event-driven пробуждение диспетчеров

**Статус:** частичная реализация находится в PR #61, но обязательное предварительное одобрение заказчика комментарием в PR не подтверждено. Реализация была начата преждевременно; общее указание продолжать не заменяет явное одобрение RFC. Дальнейший переход ожидает решения заказчика.
**Дата:** 2026-11-25.
Включается через `NEXUS_LISTEN_DSN`: отдельный listener для web и отдельного lab worker, транзакционные подсказки для задач и lab runs в миграции `0045`. Повторные сигналы одной очереди объединяются с минимальным интервалом 0,5 с (начальный rescan при подключении выполняется отдельно), поэтому задержка 10–50 мс не гарантируется. Planning-очередь, нагрузочные испытания и остальные варианты из RFC ещё не реализованы/не проверены. Связанный документ: [ADR-005](nexus-3.0/ADRs.md) — PostgreSQL остаётся устойчивой очередью, уведомление является только подсказкой.

## Цель и границы

Уменьшить задержку от фиксации готовой работы в БД до начала следующей попытки её обработки, в том числе когда API и worker находятся в разных процессах. Не менять семантику подтверждения плана, аренды, fencing, авторизации репозитория и идемпотентного запуска. Этот RFC не предлагает убрать все таймеры и не утверждает, что p99 API уже ниже 50 мс: это отдельный показатель, который требуется измерить.

## Наблюдения о текущей реализации

Проверено по коду, а не по предположениям о системе:

| Компонент | Работа в проходе и ожидание | Ограничение |
|---|---|---|
| `App._run` в `orchestration/web_server.py` | `SrRuntime.tick()`, `CloudDispatcher.tick()`, `WorkflowVerifier.tick()`, затем `self._stop.wait(poll_interval)`; значение по умолчанию — 5 с | Локального wake для очереди здесь нет. Время одного прохода добавляется к интервалу ожидания. |
| `CloudDispatcher.tick()` | `reclaim_expired`, опрос активных задач, до пяти вызовов атомарного `claim_task` за проход | Claim проверяет зависимости, подтверждение и занятость workspace. `_await_start()` опрашивает OpenHands и может блокировать проход до `start_poll_attempts * start_poll_interval`, не считая сетевых задержек. |
| `SrRuntime.tick()` и `WorkflowVerifier.tick()` | Просматривают workflows и запрашивают события/статус OpenHands | Эти внешние изменения не генерируют PostgreSQL NOTIFY сами по себе; задержка и нагрузка не исчезнут от уведомления о новой задаче. |
| `App._run_lab` | `LabWorker.tick_once()`, затем ожидание `_lab_wake` с таймаутом | `wake_lab()` будит только встроенный worker этого процесса. Запуск, возобновление, повтор и отмена из ряда HTTP-путей уже вызывают его. |
| `LabWorker.run_forever()` в `orchestration/lab_worker.py` | Проход по `active_run_ids`, scheduler, доставка долгов, очистка и heartbeat; затем `wait(poll_interval)` | Имеет локальный `wake()`; отдельный процесс получает уведомления лишь при включённом `NEXUS_LISTEN_DSN`. Таймер также обеспечивает heartbeat и восстановление. `LabScheduler.tick()` захватывает не более одной новой задачи на run за проход; burst-уведомление не гарантирует немедленную обработку всего backlog. |
| `App._run_planning` / `SpecPlanner` | `tick()`, затем `spec_planner.wait(poll_interval)`; локальный `wake()` используется при постановке и продолжении планирования | Межпроцессного уведомления нет. Таймаут нужен также для обработки оставшихся строк после сбоя. |
| `OpenHandsExecutor` в `orchestration/nexus_lab.py` | Опрос старта, продолжения и работающих conversations | Зависит от API OpenHands; PostgreSQL NOTIFY не сообщает о готовности внешнего сервиса. |
| `App._maybe_sweep()` | Очистка сессий и устаревших записей rate-limit по монотонным часам | Выполняется после основного прохода и не должна зависеть только от наличия задач. |

Это перечень polling в диспетчерских/планирующих путях, а не всех циклов проекта. Например, shutdown HTTP-сервера, диагностические пробы и экспоненциальные retry имеют иное назначение.

**Уже существующий путь подтверждения.** `Handler._launch_initial` в `web_server.py` создаёт lab run и подтверждает соответствующий hash плана через callback в той же транзакции; после успеха вызывает `wake_lab()`. Новый механизм должен уведомлять другие процессы *после commit* этой транзакции, а не запускать неподтверждённые или устаревшие планы. В системе есть также отдельная очередь `tasks` для `CloudDispatcher` и очередь lab `nexus_run_tasks`/`nexus_runs`: уведомление только о `tasks` не покрывает утверждённые lab-планы.

## Предлагаемое решение

1. Оставить БД единственным источником истины и сохранить текущие транзакции claim, lease и fencing. Дополнить каждую реально поддерживаемую транзакцию создания или разблокировки работы параметризованным `SELECT pg_notify(...)` внутри **той же транзакции**, чтобы уведомление доставлялось только после успешного commit. Использовать фиксированные имена каналов и минимальные payload без секретов; для wake достаточно типа очереди, а не данных пользователей. Точный перечень транзакций (подача `tasks`, retry/reclaim и освобождение зависимостей, создание/возобновление lab run, готовность этапов планирования) составить и покрыть тестами при реализации; не уведомлять на каждый claim/heartbeat и не создавать самоподдерживающийся цикл.
2. Для каждого процесса-слушателя открыть **отдельное сессионное соединение** к той же базе и выполнить `LISTEN`. После подтверждения регистрации выполнить полный проход, затем ждать уведомление либо таймаут; на разрыв переподключаться с ограниченным backoff, повторять `LISTEN` и снова выполнять полный проход. Уведомления могут дублироваться, объединяться или теряться: они не являются сообщениями очереди. Один канал может разбудить несколько процессов; единственность работы по-прежнему обеспечивает claim в БД.
3. Уведомлением пробуждать соответствующие локальные циклы, не дожидаясь таймера. Сохранить периодический проход при отсутствии уведомлений: внешние статусы OpenHands, истечение lease, retries, heartbeat, долги по отчётам/подписям и housekeeping зависят от времени или внешней системы. Учесть события во время прохода и перед ожиданием, остановку процесса и гонки `set/clear`; не терять пробуждение между проверкой и сном. Ограничить частоту пустых проходов и пакетировать burst-уведомления.
4. **PgBouncer:** transaction pooling непригоден для долговременного `LISTEN`; listener должен использовать прямое соединение PostgreSQL либо отдельный session-pooled endpoint. Обычные транзакции могут использовать transaction pool при проверке совместимости проекта. Учесть количество соединений при нескольких процессах и выделить отдельную конфигурацию listener DSN без публикации секретов.
5. Redis Pub/Sub и Streams в эту минимальную реализацию не включаются. PostgreSQL NOTIFY доставляется слушателям, подключённым к одной БД, в том числе в разных процессах/хостах; Redis не нужен для такого fan-out. Для Redis, кэшей и межсервисных потоков нужны отдельные решения о надёжности, инвалидировании и развёртывании. MinIO, WebSocket и async-реорганизация — отдельные задачи.

## Безопасность, развёртывание и откат

NOTIFY доступен другим сессиям этой БД: payload не содержит токены, промпты, логи или приватные сведения. Соединение listener использует минимальные привилегии и TLS в соответствии с настройками deployment. Ограничить интенсивность отправки и обработку некорректных payload; уведомление никогда не обходит проверки прав. Проверить состояние очереди уведомлений и влияние долгих транзакций, добавить метрики переподключений и задержки обработки. При недоступности listener система продолжает опрашивать БД по таймеру; флаг включения позволит отключить новый путь без отмены сохранённых задач. Реальные DDL-миграции должны быть additive и idempotent; номер выбирается по состоянию репозитория на момент реализации, а не резервируется этим RFC.

## Проверка перед включением

- Unit: пробуждение и остановка, burst и дубликаты, уведомление во время прохода/перед ожиданием, таймаут, отказ и повторное соединение.
- PostgreSQL integration: уведомление видимо только после commit, не видно после rollback; listener зарегистрирован до тестового commit; восстановление после disconnect; отдельные процессы API и worker; подтверждение именно актуального hash плана и запрет дублирующего запуска; параллельные workers не нарушают claim/fencing/workspace-lock.
- Сравнить обычный режим и режим с отключёнными/потерянными NOTIFY: работа всё равно обрабатывается по таймеру, heartbeat и lease работают, а при всплеске нет бесконечного цикла уведомлений.
- Нагрузочный тест на PostgreSQL и реальных или явно описанных имитаторах OpenHands: отдельно измерить p50/p95/p99 **commit→claim** и HTTP read latency, throughput, ошибки, нагрузку БД, pool connections; сценарий минимум со 100 одновременными агентами, отдельное измерение базовой версии и новой, конфигурация и число запросов зафиксированы. Цель 10–50 мс для пробуждения и p99 чтения API <50 мс — гипотезы/критерии пользователя, не гарантии данного RFC. Сетевые вызовы, длительный проход и конкуренция могут доминировать.

## Открытые решения для утверждения

- Включать уведомления сначала для обеих очередей (`tasks` и lab runs) или поэтапно; рекомендуемый безопасный порядок — lab approval/start, затем legacy dispatcher и planning.
- Указать безопасный direct/session DSN для listener в production, лимит подключений и метрики.
- Установить допустимую верхнюю границу fallback-таймера и пороги нагрузочных испытаний на целевой инфраструктуре.

**Следующий шаг:** проверить остальные случаи восстановления и нагрузку в целевой инфраструктуре; решение распространять на planning принимать по результатам тестов.
