# Full project audit — 2026-11-20

An evidence-based audit of what NEXUS does today, what is left, how long the
tests take, and how it performs. Every claim names how it was checked. Nothing
here is an estimate where a measurement was possible.

**Method.** The repository was read, not its docs: the status rows were
cross-checked against real test files, `TODO`/`FIXME`/`NotImplementedError` were
grepped, the server was started and driven over real sockets, and the benchmark
and test suites were run on this machine.

## 3. What is left

Read from `docs/PRODUCT_ROADMAP.md` and verified against the code — a "gap"
below was checked to still be a gap.

### Real work remaining

1. **Bounded autonomous replanning** — PARTIAL. A durable run *reworks* a task
   that fails verification; it does not *invent new tasks* from the failure
   evidence. This is the last piece of the autonomous loop. It needs a safety
   review because the obvious implementation can loop forever; the design is
   bounded (new tasks depend on the failure, the DAG is re-validated,
   iterations and deadline capped, the run goes BLOCKED at the budget).
   **Effort: the largest single item left — days, not hours.**

2. **Studio screens for the remaining backend-only routes.** Verified by
   grepping the studio for each: `voice`, `allowlist`, `diagnostics` (now done),
   `github create/visibility` have **zero** UI references while their routes
   exist and are tested. The evidence viewer and the diagnostics screen are now
   done; File Lab uploads, workspaces, voice notes, plan approval, GitHub
   create/visibility and the allowlist editor are not.
   **Effort: one screen per capability, each a day or so — the pattern is
   established (settings tab + `data-action` handler + a Chromium journey).**

3. **Runtime verification of the client packages.** The APK and the `.exe` are
   built and their binaries inspected, but never run: no Android emulator
   (`/dev/kvm` absent) and no Windows host here.

### External blockers (not defects)

- **A second live OpenHands key** — two-account failover is proven only against
  the local fakes + PostgreSQL.
- **A GitHub provider token on the OpenHands account** — a live task that must
  push ends `completed_unverified`, which is the correct, honest outcome.
- **An Android emulator / a Windows host.**
- **Owner authorisation** to merge, tag or deploy.

### Deliberately out of scope

Multi-user IAM (single-owner by design), an MCP *client*, office-document
previews, a native iOS app.

## 6. Defects found and fixed by this audit

An audit that finds nothing is an audit that looked at nothing. Three real
defects came out of it.

### 6.1 A 140× slowdown from PostgreSQL's JIT — fixed

`LabStore.queue_cleanups`, the worker's retention scan, runs on every pass. Its
plan unions five sources with `jsonb_array_elements` lateral joins, which the
planner prices in the millions, so **PostgreSQL's JIT compiled it**: 500–670 ms
of compilation for a query that then returned zero rows in microseconds.

- **Measured**: 635 ms → **4.5 ms** (p50) with the project's own benchmark.
- **Fix**: `PostgresStore` opens every connection with `jit = off`
  (`cloud_store._jit_options`); `NEXUS_DB_JIT=on` restores the server default.
- **Rejected approaches, recorded so nobody repeats them**: an index on the
  conversation columns (581 → 579 ms), and raising `jit_above_cost` to 10⁷
  (still 600 ms — the estimate exceeds it).
- **Pinned** by `tests/test_jit_settings.py` (16 cases, mutation-proven: remove
  the option and two of them fail).

### 6.2 The benchmark leaked state that starved the queue — fixed

`benchmarks/scheduler_bench.py` reset the schema on the way in but left its runs
behind: 2 050 tasks in `dispatched` and 5 runs still `running`. Those hold the
global in-flight budget, so **every real claim was refused** until their leases
expired. It now resets the schema on the way out; a run leaves 0 runs, 0 tasks.

### 6.3 The diagnostics had no screen — fixed

The diagnostic report (18 checks, the operator's health view) was reachable only
by CLI or API. The Studio's settings now has a **Диагностика** tab that renders
every check with its own status and reason. Verified live in Chromium: it showed
"7 VERIFIED · 2 FAILED · 2 BLOCKED · 4 UNVERIFIED" and explained each one — and
the 2 FAILED were how defect 6.2 was found.

## 7. Verdict

**A working product with one significant feature left.** The development loop
runs end to end — verified live this session: a real OpenHands conversation was
created, ran a shell command, uploaded a file and read it back with a matching
SHA-256, and reached `finished` (18 VERIFIED / 0 FAILED / 0 BLOCKED on the live
diagnostics). Reads are a few milliseconds under a thousand requests a second.
The suite is green in ~8 minutes.

What is left is **bounded replanning** (the last piece of autonomy, and the one
that needs the most care), **UI for capabilities that already work through the
API**, and **runtime testing of the packaged clients** — which needs hardware
this environment does not have.
